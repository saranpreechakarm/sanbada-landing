# ผลตรวจ Responsive และความปลอดภัย — 18 พฤศจิกายน 2026

ตรวจซอร์ส Laravel และเว็บ local ของ Sanbada ในโฟลเดอร์ `C:\MAMP\htdocs\adpage\sanbada-landing` พร้อมทดสอบบนฐานข้อมูล SQLite แยก และตรวจการติดตั้งกับ MySQL เดิมก่อนส่งมอบ

## สิ่งที่ปรับแล้ว

- แยก Leads/CSV/แดชบอร์ดไว้หลังการเข้าสู่ระบบและสิทธิ์ผู้ดูแลเว็บไซต์ ผู้ใช้ทั่วไปและผู้ใช้ LINE CRM ที่ไม่มีสิทธิ์เว็บเข้าไม่ได้
- คง CSRF ทุกฟอร์ม ยกเว้น LINE webhook ที่ตรวจ HMAC ตามระบบเดิม ทดสอบ POST ที่ไม่มี CSRF ว่าถูกปฏิเสธ
- จำกัดการส่ง Lead ตาม IP และเบอร์โทร เพิ่มช่องดักบอต ปฏิเสธไฟล์แนบในฟอร์มสาธารณะ และจำกัด payload ฟอร์มไว้ 32 KB
- ใช้ข้อมูลโครงการจากฐานข้อมูลจริง ไม่เชื่อชื่อโครงการ สถานะ หรือแหล่งที่มาที่ผู้ส่งกำหนดเอง
- จำกัดชนิดและขนาดไฟล์ ตรวจ MIME/รูปภาพ/มิติ ตั้งชื่อไฟล์สุ่ม เก็บ PDF นอก public และป้องกันการรันไฟล์สคริปต์ใน uploads สำหรับ Apache
- ตรวจสิทธิ์ดาวน์โหลด PDF และ realpath ป้องกันการข้ามโฟลเดอร์
- ข้อความลูกค้า โครงการ และบันทึกแสดงผ่านการ escape; ทดสอบ payload XSS และ SQL injection
- CSV ใช้การ quote มาตรฐาน พร้อมทำให้เซลล์ที่อาจเป็นสูตรถูกอ่านเป็นข้อความ
- หน้าแอดมินมี CSP ที่ไม่อนุญาตสคริปต์ inline, ป้องกันการฝังหน้าแอดมิน, no-store และ no-referrer; เพิ่ม nosniff ให้ response ผ่านแอป
- ต้องยืนยันรหัสผ่านปัจจุบันก่อนเพิ่มหรือเปลี่ยนสิทธิ์ผู้ดูแล/ตั้งรหัสให้บัญชีอื่น เซสชันเดิมใช้ต่อไม่ได้หลังเปลี่ยนรหัสผ่าน
- ปิด debug โดยบังคับเมื่อ APP_ENV เป็น production และใช้ Secure cookie เป็นค่าเริ่มต้นใน production

## Dependency audit

ก่อนปรับ Composer รายงาน 57 รายการคำเตือนใน 15 แพ็กเกจ รวมรายการระดับ critical/high บางรายการเป็นแหล่งข้อมูลซ้ำของ advisory เดียวกัน จึงไม่ใช่จำนวนช่องโหว่ที่ยืนยันว่าโจมตีเว็บนี้ได้ทั้งหมด

อัปเดต Laravel จาก 12.44.0 เป็น 12.73.0 และแพ็กเกจที่เกี่ยวข้องภายในข้อกำหนดของโปรเจกต์ โดยตั้ง Composer platform เป็น PHP 8.2 เพื่อรักษาความเข้ากันได้กับข้อกำหนดเดิม ทดสอบจริงด้วย PHP 8.4.4

ผลหลังปรับ:

| การตรวจ | ผล |
| --- | --- |
| `composer audit --locked` | 0 advisories |
| `npm audit --omit=dev` | 0 vulnerabilities |
| `npm audit` รวมเครื่องมือพัฒนา | ยังมี 6 รายการระดับ high ในสาย dependency picomatch/fdir/tinyglobby/Vite/plugin |

รายการที่ยังเหลืออ้างถึง [picomatch ReDoS advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) โดย registry ไม่เสนอแพตช์ตรงช่วงเวอร์ชันปัจจุบัน และ `npm audit fix --force` เสนอให้ลด Vite ข้าม major ซึ่งไม่ได้นำมาใช้ เครื่องมือกลุ่มนี้ใช้ build/dev ไม่ได้ถูกรวมเป็นโค้ด runtime ที่ส่งเข้าเบราว์เซอร์ ควรติดตามแพตช์และไม่เปิด dev server สู่เครือข่ายภายนอก

Node ในเครื่องคือ 20.15.1 ซึ่งต่ำกว่ารุ่นที่ Vite ระบุว่ารองรับ (20.19+ หรือ 22.12+) แม้ build ครั้งนี้ผ่าน ควรอัปเดต Node ที่ใช้ build หลังตรวจผลกระทบกับโปรเจกต์อื่นในเครื่อง

## จุดที่ต้องตั้งค่าบนโฮสติ้ง / เครื่องเซิร์ฟเวอร์

1. ตั้ง DocumentRoot ไปที่ `public` เท่านั้น ปฏิเสธ `.env`, `.git`, vendor, storage, source และไฟล์สำรองจาก HTTP ไม่วางไฟล์ SQL สำรองใน public
2. ใช้ HTTPS, `APP_ENV=production`, `APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true` และตั้ง APP_URL ให้ตรงโดเมนจริง
3. ใช้บัญชีฐานข้อมูลเฉพาะแอปและสิทธิ์เท่าที่จำเป็น ปิดการเข้าถึงฐานข้อมูลจากภายนอกหากไม่ต้องใช้
4. การตรวจ local พบ MySQL ของ MAMP ฟังที่ `::` พอร์ต 3306 ซึ่งอาจรับจาก interface เครือข่ายด้วย ทั้งนี้ขึ้นกับระบบและ firewall **ยังไม่ได้เปลี่ยนบริการ MySQL กลางของเครื่อง** เพราะมีฐานข้อมูลโปรเจกต์อื่นใช้ร่วม ควรจำกัด bind/firewall ให้เหลือปลายทางที่จำเป็นก่อนใช้กับเครือข่ายที่ไม่เชื่อถือ
5. เซิร์ฟเวอร์ local สำหรับดูงานใช้ `127.0.0.1:8124` ไม่ใช้ PHP built-in server เป็น production server
6. บน Nginx ต้องตั้งไม่ให้โฟลเดอร์ uploads รัน PHP/สคริปต์ เพราะ `.htaccess` ใช้เฉพาะ Apache ตั้ง request body limit สำหรับฟอร์มสาธารณะให้ต่ำ และแยกจากเส้นทางอัปโหลดแอดมิน
7. สำรองฐานข้อมูล รูป/PDF และ config อย่างสม่ำเสมอ พร้อมทดสอบการกู้คืนและทบทวนบัญชีผู้ดูแลที่ยังใช้งาน

ข้อ 1–7 ต้องตรวจซ้ำบนโฮสต์จริง การตรวจนี้ไม่ได้สแกนหรือเจาะระบบโฮสติ้งภายนอก ไม่รับรองว่าระบบปลอดช่องโหว่ทั้งหมด และผล audit อาจเปลี่ยนเมื่อมี advisory ใหม่

## Responsive และการใช้งานที่ตรวจ

- หน้าเว็บ: 320×568, 390×844, 768×1024, 1024×768, 1440×900 และ 844×390 ผ่านเบราว์เซอร์ Chromium
- ตรวจ New Projects/วิดีโอแบบสไลด์และเห็นการ์ดถัดไปบนมือถือ ขนาดการ์ดประมาณ 243–280 พิกเซลตามหน้าจอ
- ตรวจเมนูแท็บเล็ต/มือถือ ไม่พบ document ล้นแนวนอนในขนาดที่ทดสอบ
- ฟอร์มติดต่ออยู่ใน viewport มีช่องกรอกขึ้นก่อนข้อความแนะนำ ล็อกการเลื่อนฉากหลังและซ่อนวิดเจ็ตขณะเปิดฟอร์ม
- ตรวจเปิดวิดีโอแนวตั้งในหน้าต่างแยกที่พอดีกับ viewport พร้อมภาพหน้าปกจริงจาก YouTube
- ตรวจหลังบ้าน Leads/แดชบอร์ด/โปรเจกต์/วิดีโอ/ผู้ดูแล ในขนาด 320, 768 และ 1440 พิกเซล ไม่พบ document ล้นแนวนอน
- ทดลองส่งคำขอจากหน้าเว็บ พบรายการใน Leads แล้วบันทึกสถานะ ผู้ดูแล โน้ต และนัดติดตามได้จริงในฐานข้อมูลทดสอบแยก

การจำลองขนาดจอไม่แทนการทดสอบ Safari/iOS/Android บนอุปกรณ์จริงทุกแบบ ควรตรวจเพิ่มกับอุปกรณ์ที่กลุ่มลูกค้าใช้งานหลักก่อนปล่อยขึ้นโฮสต์จริง
